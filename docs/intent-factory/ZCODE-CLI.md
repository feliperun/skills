# ZCode CLI: how Z.ai's official harness works

A reference for the **ZCode** CLI (Z.ai's official harness for the GLM models)
focused on headless mode, which is what intent-factory consumes through the
`zcode` driver. Everything here was measured against CLI version **0.16.5**
(ZCode app 3.11.2, macOS arm64) on 2026-09-10: what carries ✅ was verified
live; what carries 🧩 was read straight from the bundle (`zcode.cjs`) and not
exercised.

---

## 1. What it is

ZCode presents itself as a single product with two surfaces:

- **Desktop app** (Electron, "Agentic Development Environment"), documented at
  [zcode.z.ai](https://zcode.z.ai/en);
- **CLI** — a ~12.6 MB Node bundle the app embeds, which also runs on its own,
  with an interactive TUI **and** a single-prompt headless mode.

It is the same engine: this session, for instance, runs inside ZCode. The CLI is
the `claude` (Claude Code) analogue for the GLM ecosystem, with one important
difference: **there is no separate CLI installer**. The binary lives inside the
app.

## 2. Where everything lives (default macOS install)

| Artifact | Path |
| --- | --- |
| App | `/Applications/ZCode.app` |
| CLI bundle | `/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs` |
| Desktop data | `~/.zcode/v2/` (`setting.json`, `config.json`, `credentials.json`) |
| CLI data | `~/.zcode/cli/` (`config.json` expected here, `log/`, `db/`, `rollout/`, `plugins/`) |
| Embedded plugins | `/Applications/ZCode.app/Contents/Resources/glm/packages/` |

Installing the app leaves **no `zcode` executable on `PATH`**. For automation,
write a shim. The critical detail: **the CLI needs Electron's embedded Node** —
under a system Node (asdf 24.9.0 x64) the response path breaks with
`Cannot perform ArrayBuffer.prototype.slice on a detached ArrayBuffer`.

```sh
#!/bin/sh
# ~/bin/zcode — ZCode CLI shim
ELECTRON_RUN_AS_NODE=1 exec /Applications/ZCode.app/Contents/MacOS/ZCode \
  /Applications/ZCode.app/Contents/Resources/glm/zcode.cjs "$@"
```

✅ `zcode --version` → `0.16.5`; ✅ `zcode doctor` reports `process: zcode-cli`,
`default artifact: node-bundle`.

## 3. Commands

Output of `zcode --help` (0.16.5):

```
app-server  Run the ZCode Protocol stdio app server
commands    List custom slash commands
doctor      Inspect runtime and packaging assumptions
login       Sign in with Z.AI OAuth for model access
logout      Remove the shared Z.AI login credentials
plugins     List and enable installed plugins
skills      List local skills
tui         Open the terminal UI
version     Print the CLI version
```

- With no command it opens the TUI. 🧩 `app-server` is the stdio protocol the
  desktop app uses to drive the engine — not explored here.
- ✅ `login` accepts variants (visible in the slash command's help):
  `zai-coding-plan`, `bigmodel-coding-plan`,
  `zai-coding-plan-api-key <api-key>`, `bigmodel-coding-plan-api-key <api-key>`.
  Login **writes the final API key into the CLI's `config.json`**.

## 4. Headless mode (what automation uses)

Verified way to run one prompt without the TUI:

```sh
zcode --prompt "Reply with exactly: pong" --json --mode plan --cwd /tmp/x --no-color
```

| Flag | Purpose | Status |
| --- | --- | --- |
| `--prompt <text>` | Run a single prompt and exit | ✅ |
| `--json` | Print the result as machine-readable JSON | ✅ |
| `--mode <mode>` | `build`, `edit`, `plan` or `yolo` (default `yolo` for `--prompt`) | ✅ |
| `--permission-mode <mode>` | Legacy alias (`default`, `build`, `edit`, `plan`, `yolo`) | 🧩 |
| `--resume <sess_...>` | Resume a persisted session by id | ✅ |
| `-c, --continue` | Resume the directory's last session | 🧩 |
| `--cwd <path>` | Run as if in that directory | ✅ |
| `--attach <path>` | Attach a local file to `--prompt` (repeatable) | 🧩 |
| `--surface terminal\|desktop` | Headless presentation surface | 🧩 |
| `--target <text>` | Set/pursue a session objective | 🧩 |
| `--no-color`, `--verbose`, `--locale` | Presentation/diagnostics | ✅/🧩 |
| `--browser-use headless`, `--browser-executable <path>` | Browser Use backend | 🧩 |

### ⚠️ Phantom flags in the 0.16.5 help

`--help` documents options **the parser rejects**:

- `--max-turns <n>` → `Unknown option`
- `--settings <path>` → `Unknown option`
- `--allowed-tools` / `--disallowed-tools` → `Unknown option`

The help is out of date with respect to the parser. Do not build automation on
them without testing against the target version.

## 5. Layered configuration

The effective config is a merge across layers (🧩 order observed in the bundle:
defaults → user config → project config → env, with env winning):

### 5.1 Environment variables (`ZCODE_*`)

🧩 Mapping extracted from the bundle's env parser:

| Variable | Effect |
| --- | --- |
| `ZCODE_MODEL` | Main model, as `model` or `provider/model` (e.g. `glm/glm-5.3`) |
| `ZCODE_BASE_URL` | Overrides the baseURL of the `ZCODE_MODEL` provider |
| `ZCODE_API_KEY` | Last API-key candidate in auth resolution |
| `ZCODE_STORAGE_DIR` / `ZCODE_SESSION_DB_PATH` | Relocate storage/sessions |
| `ZCODE_HTTP_PROXY` / `ZCODE_NO_PROXY` / `ZCODE_AGENT_CA_CERT` / `ZCODE_HTTP_TIMEOUT` | Network (the desktop app ignores the ambient `HTTP_PROXY`) |
| `ZCODE_LOG_DIR` / `ZCODE_LOG_FORMAT` (`text\|json`) / `ZCODE_LOG_CONSOLE` | Logging |
| `ZCODE_MAX_TOOL_CONCURRENCY` | Tool concurrency |
| `ZCODE_DATA_BASE_DIR` | Alternative data root (`~/.zcode`) |
| `ZCODE_TELEMETRY_*`, `ZCODE_DEBUG` | Telemetry/diagnostics |

✅ `ZCODE_MODEL` + `ZCODE_BASE_URL` alone configure a complete call — no file
needed.

### 5.2 User config — `~/.zcode/cli/config.json`

With no model configured the CLI dies with:
`Error: Model config is missing. Create ~/.zcode/cli/config.json with an
explicit model provider before running ZCode.` ✅

🧩 Model block schema (model entries **register the providers**; there is no
independent `providers` block):

```json
{
  "model": {
    "main":  { "provider": "glm", "kind": "anthropic", "baseURL": "https://api.z.ai/api/anthropic", "model": "glm-5.3" },
    "lite":  { "provider": "glm", "model": "glm-5.3-flash" },
    "available": [ { "provider": "glm", "model": "glm-5.3-flash" } ]
  },
  "permission": { },
  "network": { },
  "storage": { },
  "plugins": { },
  "hooks": { }
}
```

Each entry accepts `kind` (`anthropic`, `openai`, `openai-compatible`),
`baseURL`, `apiKey` (inline) and `apiKeyEnv` (variable name). A target
`"glm/glm-5.3"` whose provider has no implicit entry becomes
`openai-compatible` with no baseURL and fails with `Model provider glm is
missing baseURL`. ✅ (observed message)

### 5.3 Project config — `<repo>/zcode.json` or `<repo>/.zcode/config.json`

🧩 The CLI discovers per-project config at these two paths (the basis of the
app's **workspace hooks** system: per-repository `hooks`, with `hooksRoot`
{`enabled`, `timeoutMs`, `maxOutputBytes`}). The model layer merges too.

### 5.4 Builtin providers

🧩 Template embedded in the bundle:

| Provider id | baseURL | Template models |
| --- | --- | --- |
| `zai` (Z.AI Coding Plan) | `https://api.z.ai/api/anthropic` | `zai/glm-5.1`, `zai/glm-4.7` (outdated) |
| `bigmodel` (BigModel) | `https://open.bigmodel.cn/api/anthropic` | `bigmodel/glm-5.1`, `bigmodel/glm-4.7` |

⚠️ **The `zai` provider route is special** (it signs/routes coding-plan
requests). Without the CLI's own login it answers **404 Not Found**, even with a
valid API key — ✅ verified. Using a **neutral provider id** (`glm`) +
`ZCODE_BASE_URL`, the direct Anthropic-compatible call works with no OAuth. ✅

## 6. Authentication

Per-provider API-key resolution order (🧩 `resolveApiKey` in the bundle):

1. `apiKey` inline in the provider entry (config);
2. Environment variable: the entry's `apiKeyEnv`, otherwise the `kind` default
   (`anthropic` → `ANTHROPIC_API_KEY`, `openai` → `OPENAI_API_KEY`), **plus**
   the provider-name derivatives — `<PROVIDER>_API_KEY` (`glm` → `GLM_API_KEY`,
   `zai` → `ZAI_API_KEY`) — **plus** `ZCODE_API_KEY`;
3. `anthropic`/`openai`/`gateway` providers **require** a key: without any,
   `Error: Model provider <id> is missing an API key: <id>`. ✅

The variable read is the CLI process's `process.env` (no filtering). OAuth
(`zcode login`) shares credentials with the desktop app
(`~/.zcode/v2/credentials.json`: `oauth:zai:access_token`, `zcodejwttoken`), 🧩
but the CLI keeps its own copy of the key in `config.json`.

## 7. Models

Verified against the coding-plan endpoint (Z.AI, `api.z.ai/api/anthropic`):

| Model id | Status |
| --- | --- |
| `glm-5.3` | ✅ works; 1M window reported in the session projection |
| `glm-5.3-flash` | ✅ works |
| `glm-5.3-pro` | ❌ `400 invalid_request_error` — `[1211][Unknown Model…]` |
| `glm-5.3-air` | ❌ `400` Unknown Model |

"Pro" is a **subscription-plan tier**, not a model id. The app's catalogue lists
`GLM-5.3` with reasoning variants `low`/`max`/`high` (default `max`), 🧩 but CLI
0.16.5 exposes no reasoning-effort flag — the model picks the depth. The `[1m]`
suffix is the Claude Code CLI's convention for the 1M-context tier; ZCode does
not know it (the window comes from the provider), and a `[1m]` inside a model id
yields Unknown Model. ✅

## 8. `--json` output

Headless prints **a single JSON object** (it is not an NDJSON event stream like
claude's `--output-format stream-json`). Real shape ✅:

```json
{
  "sessionId": "sess_bf4de980-bd3a-43a1-9884-b88d610bf2a9",
  "traceId": "7ceb9c1a-d04f-4691-b2ff-b83f45c2db53",
  "turnId": "turn_aa9444ba-99b0-46b5-8675-077bcd008e71",
  "response": "pong",
  "usage": {
    "source": "provider",
    "modelRequestCount": 1,
    "inputTokens": 15506,
    "outputTokens": 109,
    "totalTokens": 15615,
    "cacheReadTokens": 9024,
    "cacheWriteTokens": 0,
    "reasoningTokens": 0,
    "webFetchRequests": 0,
    "webSearchRequests": 0
  },
  "eventCount": 118,
  "projection": {
    "status": "idle",
    "turnCount": 1,
    "totalTokenCount": 15615,
    "contextUsed": 15615,
    "contextWindow": 1000000
  }
}
```

Points that matter to whoever measures:

- **`inputTokens` already includes cache reads** — `totalTokens = inputTokens +
  outputTokens`. For "uncached input", subtract `cacheReadTokens`. ✅
- `eventCount` counts the session's internal events; they are not exposed.
- **Cost is not reported** (nothing equivalent to claude's `total_cost_usd`).
- Failure before the result: **empty stdout + diagnostics on stderr**, e.g.
  `Error: Model provider is missing an API key: zai` ✅ or
  `Error: Turn execution failed (traceId: …)` ✅. Output parsers must treat
  "no JSON" as a normal error path and read stderr.

## 9. Sessions and continuation

- `--resume <sess_...>` resumes persisted context: ✅ on the second call the
  cache read jumped to ~14.8k of ~15.6k input (nearly all cached) and the answer
  demonstrated memory of the previous turn.
- Sessions live in the CLI's storage (`~/.zcode/cli`, relocatable via
  `ZCODE_STORAGE_DIR`/`ZCODE_DATA_BASE_DIR`). 🧩
- `-c/--continue` resumes the cwd's last session (🧩 help; claude's `--continue`
  analogue).

## 10. Tools and permission modes

| Mode | Behaviour | Verification |
| --- | --- | --- |
| `plan` | Read-only/analysis | ✅ prompts answered without touching files |
| `build` | Inspection/execution tools | ✅ read `note.txt` through the `Read` tool and returned its content |
| `edit` | File editing | 🧩 (the factory uses it for workers) — see the measured note below |
| `yolo` | Everything, no approval requested; **default of `--prompt`** | 🧩 help; the factory uses it for autonomous workers |

- **There is no way to restrict the tool list per invocation** in 0.16.5
  (`--allowed-tools`/`--disallowed-tools` are phantom flags). The mode is the
  only control. A driver that needs mechanical tool policy (hooks) does not have
  one — which is why the factory's `zcode` driver declares `toolPolicy: false`
  and `permissions: false`.
- 🧩 Per-project hooks exist (`zcode.json`/`.zcode/config.json`, `hooks` field),
  but there is no per-invocation surface to inject them.

## 11. Structured output

There is no schema/structured-output flag in the CLI. 🧩 The bundle's provider
layer knows `structuredOutputMode` (`"outputFormat" | "jsonTool" | "auto"`) via
the config's `providerOptions`, but there is no way to pass it per invocation.

The pattern the factory adopted: **the schema travels inside the prompt text**
(the `zcode` driver embeds the `JUDGE_SCHEMA` when it receives `options.schema`)
and validation stays at the review boundary (`parseJudge` + bounded re-ask). It
works: in the end-to-end run the `glm-5.3` judge returned the verdict exactly on
schema. ✅

## 12. Cost, preamble and performance

- Preamble observed (trivial prompt, plan mode): **~15.3–15.5k input tokens**
  per cold call, with 2.9–9k cache read on the first call and ~14.8k when
  resuming a session. ✅
- Same-scale comparison: the factory's "dieted" claude-code route measures ~4.3k
  input/turn. ZCode's native preamble is heavier; its advantage is a native
  protocol (tool calling in GLM's format) and independence from the
  Anthropic-compatible shim.
- Live metering mid-run is impossible by design (output only exists at the end);
  usage is in the terminal envelope only. ✅

## 13. Known quirks (0.16.5)

| Quirk | Detail | Workaround |
| --- | --- | --- |
| Stale help | `--max-turns`, `--settings`, `--allowed-tools`/`--disallowed-tools` rejected by the parser | Test every flag against the target version before depending on it |
| System Node breaks | `detached ArrayBuffer` on the response path (Node 24 x64) | Run with Electron's Node (`ELECTRON_RUN_AS_NODE=1 …/MacOS/ZCode …/zcode.cjs`) |
| `zai` provider 404s without login | The coding-plan route signs requests; without `zcode login` it 404s even with a valid key | Neutral provider id (`glm`) + `ZCODE_BASE_URL` |
| Cache-inclusive `inputTokens` | `totalTokens = input + output` | Subtract `cacheReadTokens` for cold input |
| No cost, no stream, no schema flag | Single terminal envelope | Parsers oriented to "final object + stderr" |
| "Pro" is not a model | `glm-5.3-pro` → Unknown Model | Use `glm-5.3` (strong judge) / `glm-5.3-flash` (worker) |

## 14. How the factory uses it (summary of the `zcode` driver)

- Executable: `INTENT_FACTORY_ZCODE_BIN` → `runtime.executable` → `zcode` on
  `PATH`. When that name resolves to nothing, the adapter installs the section 2
  shim itself onto `PATH` (intent-factory's change of 2026-09-11; the original
  text here described the shim as a manual prerequisite).
- Per invocation the driver injects: `ZCODE_MODEL=<provider>/<model>`
  (provider from `config.provider`, default `glm`; `[1m]` suffix removed),
  `ZCODE_BASE_URL` (default `https://api.z.ai/api/anthropic`),
  `<PROVIDER>_API_KEY` with the token from the `auth_token.env_key` →
  `ZAI_API_KEY` → `ANTHROPIC_AUTH_TOKEN` chain, and removes the ambient
  `ANTHROPIC_API_KEY` (the CLI tests it first).
- The runtime's `permissionMode` becomes `--mode`; continuation via
  `--resume sess_…`; prompt via `--prompt` (128 KB argv limit); the judge schema
  is embedded in the prompt; `structuredOutput`/`toolPolicy` are declared
  `false` honestly.
- Live preflight: the 15s default is short for ZCode's preamble — use
  `INTENT_FACTORY_PREFLIGHT_TIMEOUT_SEC=60`.
- Example runtime in a contract:

```json
{
  "zcode-flash": { "driver": "zcode", "model": "glm-5.3-flash", "vendor": "zhipu-flash", "permissionMode": "edit" },
  "zcode-pro":   { "driver": "zcode", "model": "glm-5.3", "vendor": "zhipu-pro", "permissionMode": "plan" }
}
```

Distinct vendors are mandatory when the gate crosses worker × judge of the same
family (see [contract.md](../../skills/mine/intent-factory/references/contract.md)).

## Measured by intent-factory

Our own observations, kept apart from the vendor text above. Where they disagree
with it, this section is the current truth about the driver, not about the CLI.

- **`edit` does not execute commands** (measured 2026-09-10,
  `.runs/if-live-drivers-20260910`). Worker `live-zcode`, `driver: zcode`,
  `model: glm-5.3-flash`, `permissionMode: edit`: the worker wrote its file and
  then reported that its shell verification could not run —
  `No permission client configured for Bash`, 2 attempts
  (`logs/live-zcode.1.worker.jsonl`). This upgrades section 10's `edit` row from
  🧩 to measured on the file-editing side, and it corroborates the adapter's
  `permissionExecution.executingModes: ["yolo"]`. The `yolo` row stays 🧩: no
  intent-factory run has exercised it yet.
- **The shim is no longer a manual prerequisite.** `ensureZcodeAvailable` in
  `scripts/drivers/zcode.mjs` writes the section 2 shim when `zcode` resolves to
  nothing on `PATH`, into the first of `~/.local/bin`, `~/bin`, `/usr/local/bin`
  that is both on `PATH` and writable. It never writes through a symlink and
  never rewrites a file whose bytes already match, so a hand-installed
  `zcode -> zcode-shim` is untouched. `executable()` still returns the bare name
  `zcode`: the runtime fingerprint hashes it and compares against snapshots a
  previous process persisted, and an absolute path would make session
  continuation depend on the inherited `PATH`.
- **The `[1m]` note in section 7 has a cost side.** Because the driver strips the
  suffix and the CLI ignores it, a `glm-5.3[1m]` runtime and a `glm-5.3` runtime
  were the same invocation listed twice. The `models` catalogue now declares a
  single `glm-5.3` at the 1M window (`scripts/models.mjs`).
