### O problema que sobrou

Seis retrospectivas afirmam melhoria. A de suite-speed precisou corrigir um
número da anterior: 25.257 linhas de produção viraram ~20.218 reais, porque a
contagem incluía um arquivo de teste que morava em `scripts/`. A lacuna estava
superestimada em 5.039 linhas.

Isso não é descuido. É o que acontece quando um sistema evolui por
retrospectiva em vez de por medição comparável. `metrics.mjs` mede uma campanha
por vez e faz isso bem; nada compara duas.

**A tese desta spec: a fábrica não tem mais problema de correção nem de
disciplina. Tem problema de medição e de escopo.**

## C0 — Correção imediata

Fora de bloco, entra antes de tudo.

### C0.1 Teste que exige binário real no PATH

`test/runner-worker-result.test.mjs:399`, "a second unparseable worker result
takes the failover edge before it blocks with attention".

O teste stuba `first` e `second` com `fakeCodex`, mas o runtime `judge` declara
`{ driver: "codex", model: "judge", vendor: "openai-judge" }` **sem
`executable`**. `env-preflight` resolve o binário real e para com
`env_preflight_failed: runtime binaries: judge: codex not found on PATH`.

Falha 3 de 3 em máquina sem `codex`. O CI roda `ubuntu-latest` e
`macos-latest` com `npm ci` apenas, sem `codex`. Verde só na sua máquina, que é
o defeito recorrente deste projeto.

**Correção.** Stubar `executable` no runtime `judge`, como os outros dois já
têm. Auditar todo runtime declarado em teste que não traz `executable`.

**Guarda estrutural.** Um teste novo varre os contratos de fixture e falha se
qualquer runtime de teste omitir `executable`. Sem essa guarda, volta.

| id | item | prova |
|---|---|---|
| c0.1 | a suíte passa inteira sem nenhum CLI de provedor instalado | `command: npm test` |
| c0.2 | um runtime de teste sem `executable` falha a guarda | `command: npm test -- --test-name-pattern="fixtures stub every runtime"` |
| c0.3 | o CI do `main` está verde no commit da correção | `path: .github/workflows/ci.yml` |

## ADRs novos

### ADR-0023: uma campanha não fecha sem delta medido

Toda campanha que altera comportamento da fábrica roda o golden set antes e
depois, e a retrospectiva registra o delta. Sem delta, a retrospectiva
descreve intenção, não resultado.

Justificativa empírica: a correção de 5.039 linhas da retro de suite-speed foi
possível porque alguém releu o número. Nada no sistema teria detectado.

### ADR-0024: o gate é congelado durante uma campanha de medição

Critério de gate vira objeto versionado à parte do contrato, com id e digest
próprios. Alterar o gate durante uma campanha invalida a baseline e exige nova
medição.

Herdado do EnvHarness: as intervenções ficam externas justamente para que o
verificador original continue pontuando o episódio.

### ADR-0025: redução de linhas é decisão de capacidade, não varredura

De 179 exports sem referência externa, 8 estavam mortos. Os outros 171 são
código vivo. As ~10.000 linhas acima da meta são implementação funcionando.

Consequência: **nenhuma campanha futura tem "reduzir linhas" como objetivo.**
Uma campanha de escopo nomeia a capacidade que sai, prova que ninguém depende
dela, e a remove. A contagem de linhas é efeito, nunca meta.

### ADR-0026: o modelo decide arranjo uma vez, no planejamento

O planejador propõe classificação (`taskKind`, `riskTier`); uma tabela
declarativa decide runtime. Execução consome tabela, nunca replaneja.

Se o modelo escolher o modelo, o roteamento deixa de ser comparável entre
execuções e a medição do C1 perde sentido.

### ADR-0027: evidência é gerada deterministicamente

Veredito de gate pode usar juiz. O artefato de evidência é gerado de fatos já
gravados. Nenhum LLM escreve `trace.json`. Um registro redigido por modelo é
resumo, não evidência.

### ADR-0028: status é derivado na leitura

Os snapshots de nó gravam fatos; `status` é derivado por `metrics.mjs`,
`render.mjs` e `campaign status` a partir deles. Exceção única: o artefato de
evidência sela a derivação junto com a versão que a produziu.

Última regra do agent-orchestrator ainda não adotada aqui.

## C1 — Evals

O único bloco grande que falta e o que dá sentido a todo o resto. A
infraestrutura já existe: driver `replay`, `usage.jsonl`, `events.jsonl`,
`metrics.mjs`, worktree isolado.

### C1.1 Duas classes, nunca misturadas

| Classe | Modelo | Custo | Onde | Critério |
|---|---|---|---|---|
| Determinística | não (`replay`) | zero | CI, todo PR | 100% ou falha |
| Estocástica | sim | dinheiro | sob demanda | distribuição |

Um teste que às vezes falha por variância de modelo ensina a ignorar o
vermelho. Nunca no mesmo comando, nunca no mesmo relatório.

### C1.2 Layout

    evals/
      deterministic/<case-id>/{case.yaml,recording.jsonl,expected.yaml}
      golden/<task-id>/{fixture.bundle,statement.md,verify.json,meta.yaml}
      results/<iso>-<config-id>.json
      baseline.json
      run.mjs

### C1.3 Golden set do próprio histórico

Você não precisa de SWE-bench. A construção dele é: commit pai como estado
inicial, enunciado do trabalho, testes daquele commit como verificador. Você
tem os três no repositório.

Fonte: os nós já integrados pela própria fábrica
(`b952c7b`, `c528159`, `9994efe`, `a32a2d8`, `57a35d9`, `772efa3`, `124f34e`,
`f150386`) mais commits de correção anteriores.

    evals/golden/<task-id>/
      fixture.bundle   # git bundle no commit pai
      statement.md     # taskPacket original de .runs/, ou a mensagem do commit
      verify.json      # comandos de verificação daquele nó
      meta.yaml        # runtime original, custo original, relógio original

Alvo: 20 a 30 tarefas. Nenhuma escrita à mão.

**Nota de construção.** O `statement.md` sai do `taskPacket` gravado, não é
reescrito. Reescrever o enunciado contamina a medição com a sua interpretação
posterior.

### C1.4 Casos determinísticos

Cada um injeta uma falha pelo driver `replay`.

| ID | Prova |
|---|---|
| D01 | crash entre escrita da cápsula e publicação preserva o estado anterior |
| D02 | dois `resume` simultâneos: o segundo é rejeitado pelo `controller.lock` |
| D03 | takeover de lock com pid reusado é detectado por `processStartToken` |
| D04 | quota com reset agendado retoma, não perde a tentativa |
| D05 | quota sem reset toma a aresta de `fallback` uma única vez |
| D06 | `insufficient_balance` é distinguido de `quota_exhausted` e de CLI ausente |
| D07 | parada de escopo ou autoridade nunca rotaciona runtime |
| D08 | par worker e fallback com mesmo `vendor` do juiz é rejeitado no `validate` |
| D09 | `ENOSPC` dispara GC de `.runs/` e retoma |
| D10 | prosa em vez de JSON: uma reinvocação de reparo, depois failover |
| D11 | nó órfão `running` sem processo é adotado, não re-implementado |
| D12 | nó totalmente mecânico fecha com zero invocação de juiz |
| D13 | rejeição de gate que não cita item de DoD é inválida e não consome revisão |
| D14 | `finalVerification` roda no nó terminal de fase, nunca antes |
| D15 | tentativa selada e limpa não é re-selada no retry (regressão de `6e1afef`) |
| D16 | worktree candidato herda o mesmo ambiente da tentativa (regressão de `ce675f9`) |

D15 e D16 pinam os dois defeitos de campo da retro de suite-speed. D03 e D06
pinam os da retro de gaps.

### C1.5 Indicadores comparáveis

`metrics.mjs` já projeta indicadores por campanha. O que falta é o
comparador.

    intent-factory evals run --class deterministic
    intent-factory evals run --class stochastic --config <id> --repetitions 3
    intent-factory evals compare <before.json> <after.json> [--tolerance <f>]

Indicador primário: **`costPerClosedCheckpoint`**. É o único imune ao caso em
que acurácia melhora e eficiência regride sem ninguém perceber.

Secundários, todos já derivados de `usage.jsonl` e `events.jsonl`:
`firstPassGateRate` por `taskKind`, `judgeInvocationRate`, `revisionsPerDone`,
`blockedContextRate`, `wallClockPerClosedCheckpoint`, `providerFailoverRate`,
`protocolFailureRate`.

Regra de reporte: eficácia e eficiência sempre juntas, nunca uma sozinha.

### C1.6 Admissão e aposentadoria de caso

Um caso vale enquanto fica na fronteira da capacidade atual. Caso que passa em
três medições consecutivas sai da suíte ativa e vira regressão. Sem isso a
suíte satura e para de informar.

### C1.7 Não-regressão de harness

Uma vez por release, 20 instâncias de SWE-bench Verified pela fábrica contra o
mesmo modelo no harness cru. Isso **não mede a fábrica**: mede se ela estraga o
modelo. Benchmark não é a sua base de código, e pontuações de versões
diferentes do benchmark não são intercambiáveis.

## C3 — Planejamento adversarial

O maior item nunca iniciado. Hoje o plano é autorado pela sessão de controle,
que é o custo fixo mais caro que sobrou.

### C3.1 O ciclo `plan`

    intent-factory plan <spec.md> --campaign <id> --phase <n>
      [--drivers auto|<lista>] [--review-rounds 2]

Estágios, na ordem, com o modelo entrando duas vezes só:

1. **Probe (determinístico).** Reusa `runtime-discovery` e `env-preflight`.
   Enumera drivers instalados, versão, disponibilidade ao vivo,
   `exhaustedUntil`. Emite `available-runtimes.json`.
2. **Fatos do repo (determinístico).** Inventário de paths, comandos de
   verificação disponíveis e **duração medida** de cada um. Emite
   `repo-facts.json`.
3. **Draft (frontier, uma chamada).** Recebe a spec, `repo-facts.json` e o
   catálogo de `taskKind`. Emite nós com `dependsOn`, `readFiles`,
   `writeFiles`, DoD e classificação. **Não escolhe runtime.**
4. **Roteamento (determinístico).** Tabela mapeia
   `(taskKind, riskTier, capacidade exigida)` para runtime.
5. **Revisão adversarial (driver de outro vendor).** Recebe spec, fatos e
   plano. **Não recebe o raciocínio do planejador.** Emite achados
   estruturados com severidade.
6. **Revisão com orçamento.** Achados críticos voltam ao draft, no máximo
   `--review-rounds`. Sem convergir, o plano sai `contested` e para.
7. **Congelamento.** `plan.json` e `contract.json` com digest, versão do
   pacote, e o par de runtimes que planejou e revisou.

### C3.2 Roteamento declarativo

    routingRules:
      - when: { taskKind: docs, riskTier: low }
        prefer: [deepseek-v4-flash, glm, codex]
      - when: { taskKind: implement, riskTier: high }
        prefer: [claude-opus-5, codex]
      - when: { taskKind: judge }
        forbidSameVendorAsWorker: true

`forbidSameVendorAsWorker` já é invariante no `contract.mjs`. Aqui ele passa a
ser respeitado na geração, não só na validação.

### C3.3 Dimensionamento determinístico do grafo

Regras aplicadas ao draft, não julgamento:

| Regra | Efeito |
|---|---|
| nó sem item de DoD mecânico | funde no pai |
| `writeFiles` de A contido em B, A sem verificação própria | funde A em B |
| `verification` com duração medida acima de 400 s | divide ou substitui por arquivo de teste específico |
| nós sem dependência com `writeFiles` disjuntos | podem paralelizar |
| contrato de um nó sem `--targeted-fix` | erro |
| cadeia serial com profundidade acima de 8 | exige justificativa no plano |

A terceira regra existe por causa do defeito de campo da retro de gaps: o
packet declarou `npm test` com `timeoutSec: 600` quando o arquivo levava
644,8 s. O planejador passa a **medir antes de declarar**, com o dado do
estágio 2.

### C3.4 `riskTier`

Campo novo por nó, opcional, default `standard`.

| Tier | Efeito |
|---|---|
| `low` | `failOn: critical`, `maxRevisions: 1`, runtime barato |
| `standard` | comportamento atual |
| `high` | `failOn: major`, revisor adicional de outro vendor, `finalVerification` obrigatório |

Calibra profundidade de revisão pelo risco, em vez de aplicar o mesmo gate a
tudo.

### DoD do C3

| id | item | prova |
|---|---|---|
| c3.1 | `plan` emite `plan.json` e `contract.json` válidos a partir de uma spec markdown | `command: npm test -- --test-name-pattern="plan emits valid contract"` |
| c3.2 | o revisor roda em vendor diferente do planejador | `command: npm test -- --test-name-pattern="plan review cross vendor"` |
| c3.3 | o revisor não recebe o raciocínio do planejador | `command: npm test -- --test-name-pattern="plan review isolated context"` |
| c3.4 | runtime sai da tabela, nunca da saída do modelo | `command: npm test -- --test-name-pattern="routing is table driven"` |
| c3.5 | `verification` com duração medida acima de 400 s é rejeitada no plano | `command: npm test -- --test-name-pattern="plan rejects slow verification"` |
| c3.6 | contrato de um nó sem `--targeted-fix` é erro | `command: npm test -- --test-name-pattern="plan rejects micro contract"` |
| c3.7 | `riskTier: high` exige revisor adicional e `finalVerification` | `command: npm test -- --test-name-pattern="risk tier high"` |
| c3.8 | planejar a spec de C1 custa abaixo de USD 2,00 | `command: node evals/run.mjs --plan-cost docs/intent-factory/TECH-SPEC-2026-09-09.md` |

## C4 — Camada de evidência

O diferencial que ninguém ocupou. Vercel, Ramp, Warp, Orca e Zeroshot emitem
PR e métrica de vazão. Nenhum responde por que o código existe, qual requisito
atende e qual evidência de verificação foi produzida.

### C4.1 Delimitação

O export de trace do Zeroshot é **proveniência de execução**. Reimplementar
isso é desperdício.

A camada de evidência é **ancorada no requisito**:

    requisito
      -> nó que o atende
      -> packet fechado (readFiles, writeFiles, DoD)
      -> arquivos efetivamente alterados
      -> sonda que falhava antes e passa depois
      -> comandos de verificação com exit code, duração e saída limitada
      -> veredito de gate com severidade, vendor do juiz
      -> versão do pacote, schemaVersion, versão de cada binário
      -> git HEAD antes e depois

Se o artefato responde "o que a run fez" em vez de "qual requisito foi
verificado e como", foi implementado errado.

### C4.2 Fase de nó `probe`

Herdada da Vercel: uma sonda que falha antes de implementar prova que o
requisito não estava atendido; a mesma sonda passando depois prova que passou.

É a evidência bidirecional que a IEC 62304 pede, e é mecânica.

    "phases": ["probe", "implement", "verify"]

Em `--strict-traceability`, nó de implementação sem `probe` é erro.

### C4.3 Extensão do contrato

    "requirements": [
      { "id": "SRS-042", "source": "docs/srs.md#42", "statement": "..." }
    ]

`validate` emite aviso quando um nó de implementação não declara requisito, em
modo `--strict-traceability`. Aviso, não erro: a maioria dos usos não é
regulada.

### C4.4 Integridade e exportação

Digest SHA-256 encadeado por entrada, reusando o mecanismo já existente. Cada
entrada carrega o digest da anterior, tornando remoção silenciosa detectável.

    intent-factory trace <run-dir> --format {json,markdown,csv}
    intent-factory trace ingest <external.jsonl> --map requirements.yaml

O `ingest` aceita o export de trace do Zeroshot, que é determinístico e neutro
de provedor. Isso inverte a relação competitiva a custo baixo.

### C4.5 Escopo honesto

**É:** geração automática de evidência de verificação e rastreabilidade
bidirecional entre requisito, implementação e verificação.

**Não é:** certificação, submissão regulatória, sistema de gestão da qualidade
nem substituto de revisão humana. Entra num QMS existente como insumo.

Sobreclamar aqui destrói a credibilidade que o resto do projeto construiu.

### DoD do C4

| id | item | prova |
|---|---|---|
| c4.1 | `trace` emite JSON ancorado em requisito para um run com `requirements` | `command: npm test -- --test-name-pattern="trace anchored on requirement"` |
| c4.2 | nenhum LLM é invocado durante a geração do trace | `command: npm test -- --test-name-pattern="trace is deterministic"` |
| c4.3 | remoção de uma entrada quebra a cadeia de digest | `command: npm test -- --test-name-pattern="trace digest chain"` |
| c4.4 | fase `probe` grava sonda falhando e sonda passando | `command: npm test -- --test-name-pattern="probe records both states"` |
| c4.5 | `--strict-traceability` rejeita nó de implementação sem `probe` | `command: npm test -- --test-name-pattern="strict traceability"` |
| c4.6 | `trace --format markdown` produz uma seção por requisito | `command: npm test -- --test-name-pattern="trace markdown sections"` |
| c4.7 | o trace desta própria spec é gerado e versionado | `path: docs/intent-factory/trace/TECH-SPEC-2026-09-09.md` |

## C5 — Mutation testing

O item do Uncle Bob que vale, e que agora cabe: com a suíte em 198 s, uma
entrada de mutação cabe no orçamento de tempo que antes não cabia.

### Motivação

`allowedVerification` prova que comandos passam. Não prova que o teste asserta
alguma coisa. Um worker que escreve teste vazio passa no gate hoje.

Mutation testing pega isso, é comando de shell e custa zero em modelo. Entra
como mais uma prova mecânica, reduzindo superfície do juiz. É restrição que
**economiza** token em vez de gastar, que é o tipo certo.

### Escopo

Aplicado só ao módulo tocado pelo nó, nunca ao repositório inteiro. Limiar de
score declarado no contrato, default 60% para `riskTier: standard` e 80% para
`high`.

### DoD do C5

| id | item | prova |
|---|---|---|
| c5.1 | `verification` aceita entrada do tipo `mutation` com limiar | `command: npm test -- --test-name-pattern="mutation verification entry"` |
| c5.2 | um teste que não asserta nada reprova a entrada de mutação | `command: npm test -- --test-name-pattern="mutation catches empty test"` |
| c5.3 | a mutação roda apenas nos paths de `writeFiles` do nó | `command: npm test -- --test-name-pattern="mutation scoped to node"` |
| c5.4 | a entrada de mutação de um módulo típico completa abaixo de 120 s | `command: npm test -- --test-name-pattern="mutation duration budget"` |

|---|---|---|
| 0 | C0 (teste no PATH) | CI mentindo é pior que CI ausente |
| 1 | C1.1 a C1.4 (evals determinísticos) | rede de segurança de tudo abaixo |
| 2 | C1.5, C1.8 (comparador e baseline) | sem isso, nenhuma campanha seguinte pode se justificar |
| 3 | C2.1 (split de `node.mjs`) | primeira refatoração provada por eval |
| 4 | C5 (mutation) | barato, mecânico, reduz juiz |
| 5 | C2.2 (inventário de capacidade) | insumo da decisão de escopo |
| 6 | C3 (planner adversarial) | só depois de poder provar que se paga |
| 7 | C4 (evidência) | o diferencial, depois da base estar sólida |
| 8 | C1.7 (não-regressão de harness) | uma vez por release, contínuo |

**Regra dura: C3 não começa antes de C1.5.** Planejamento adversarial usa dois
modelos e é caro. Sem comparador, você vai defender uma feature cara por
intuição, que é exatamente o modo de falha que esta spec existe para fechar.

## 7. Não-objetivos

Inalterados, mais dois:

- Webhooks de intake, identidade não-humana, SSO, RBAC, sandbox por container,
  Kubernetes, multi-tenancy, compute gerenciado.
- **Reduzir contagem de linhas como objetivo de campanha** (ADR-0025).
- **UI de gerenciamento além do `dashboard/` atual.** Ela lê o mesmo agregador
  dos evals; feita depois, sai quase de graça.

## 8. Riscos

| Risco | Impacto | Mitigação |
|---|---|---|
| Golden set derivado do próprio histórico enviesa para o que a fábrica já sabe fazer | alto | C1.6 aposenta caso saturado; C1.7 traz distribuição externa |
| C2.1 introduz regressão silenciosa | alto | vem depois de C1; c2.2 e c2.3 são bloqueantes |
| C3 dobra o custo de planejamento sem retorno | médio | c3.8 impõe teto; c3.9 exige delta medido antes de virar default |
| C4 vira mais um export de proveniência | alto | critério de C4.1: sem âncora em requisito, foi errado |
| Evals estocásticos custam mais do que entregam | médio | sob demanda, nunca em PR, orçamento fixo por execução |
| A spec vira documento morto | alto | executada pela própria fábrica, uma campanha por bloco, ADR-0023 exige delta |

## 9. Execução

Uma campanha por bloco. Cada critério de aceite acima vira item de DoD do nó
correspondente, e cada comando citado entra em `taskPacket.verification`.

Regras herdadas das retrospectivas de campo, que continuam valendo:

- Nenhum packet manda o worker rodar a suíte inteira. Verificação é do
  controlador, com o arquivo de teste específico do nó.
- Toda `verification` tem duração medida antes de ter `timeoutSec` declarado.
- Todo nó de fase terminal roda `finalVerification`.
- A campanha de C4 é a primeira a gerar evidência contra esta própria spec como
  documento de requisitos. Se a rastreabilidade funcionar para o
  desenvolvimento da rastreabilidade, ela funciona.
