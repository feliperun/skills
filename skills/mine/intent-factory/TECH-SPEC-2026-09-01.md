## 1. Load-bearing rules

Short, imperative, checked in CI where possible. They live in
`references/rules.md` and are the only normative block `SKILL.md` carries
whole.

1. **Never persist derived status.** The run directory records facts; `status`
   and `report` derive on read. The only exception is the evidence artefact,
   which seals the derivation together with the version that produced it.
2. **Never advance a cursor before the effect is confirmed.** A consumption
   cursor is an acknowledgement, not a read. Redelivery is acceptable; silent
   loss is not.
3. **Never let a cache outrun correctness state.** A cache is performance
   state. A persistence failure pins the cursor of the whole run.
4. **Never swallow an error.** An empty `catch {}` is forbidden. Legitimate
   absence (`ENOENT`) is distinguished from corruption, which emits a coded
   event.
5. **Never put a secret in model context.** Reference by variable name, never
   by value. Redaction is the second line of defence.
6. **Never let an LLM write evidence.** A gate verdict may use a judge. The
   evidence artefact is generated deterministically from recorded facts.
7. **Never change the verifier during a measurement campaign.** A gate
   criterion is a frozen object versioned apart from the contract.
8. **Never make a test depend on wall-clock time.** Signal by event or by an
   injectable clock.
9. **Never plan at runtime.** The model decides the arrangement once, at
   planning time. Execution consumes a declarative table; a node that cannot
   complete stops with bounded evidence for the orchestrator, it is never split
   or re-planned by the controller.
10. **Never expose more scope to a worker than the packet declares.** Every
    loaded instruction is a tax paid on every turn.
11. **Never authorise a serial micro-contract.** A single-node contract
    without `--targeted-fix` is an error, not a warning.
12. **Never approve a final checkpoint on partial verification.** The
    phase-terminal node runs the contract's `finalVerification`.
13. **Never wake the control session for progress.** Progress is rendered for
    humans through an ambient channel or system notification. The session is
    involved only when it must act, through an event with `requiresUser: true`.
14. **Never let the harness preamble go unmeasured.** Every driver declares
    the flags that bound its per-turn preamble, and `preflight --json` reports
    the real number per runtime at every phase start.
15. **Never run a controller from a mutable tree while workers edit it.**
    Controller and supervisor of a run start from one immutable snapshot of a
    committed HEAD; a run is never resumed through a different tree.

## 3. B1 — Pull-only feedback and ambient liveness (Addendum 01)

This section amends the session-feedback design. The control session is not a
progress dashboard: the factory never wakes it to report progress. Human
feedback is delivered through ambient state or human notification channels;
the session is involved only by an event with `requiresUser: true`.

### 3.1 Minimal event projector

`scripts/events.mjs` derives one canonical, bounded event record from a node
transition, a run terminal state, campaign attention or a phase change. The
controller and detached supervisor call it before enqueueing. `summary` and
`next` are generated from counters, never by an LLM (rule 6). Hard limit 1 KiB
per event, with `requiresUser` explicit in every record.

### 3.2 Human-channel dispatcher

The bounded campaign outbox remains the source for human notifications.
`deliveredAt` is set only after the selected transport confirms delivery
(append fsynced or `exec` exit 0). Adapters register these capabilities:

    capabilities: {
      canPush: boolean,
      canWake: boolean,
      canRenderAmbient: boolean
    }

| Channel | Consumer | Token cost | Trigger |
|---|---|---:|---|
| Claude Code `statusLine` | human at the keyboard | zero | continuously |
| OS notification | human near the machine | zero | discrete event |
| Ford (WhatsApp) | human away from the machine | zero | discrete event in a long campaign |
| control-session context | the session | 40k–80k before context diet | only `requiresUser: true` |

The detached supervisor owns the first three channels, making OS notification
harness agnostic. `canWake` is reserved for actionable events and is never a
progress transport. `canRenderAmbient: true` is verified only for Claude Code
in B1.7's current evidence boundary.

### 3.3 Heartbeat and status line

`.runs/campaigns/<id>/heartbeat.json` is a derived, atomic read cache, never a
source of truth. Facts remain append-only in `journal.jsonl`; the heartbeat is
replaced only after a successful fact write, is rebuildable from that journal,
and is bounded to 1 KiB. `lastProgressAt` records observed scope or node
progress, not event emission time. B1.6 defines the writer, macOS notifier,
Claude Code status-line script and their tests in
`ADENDO-01-feedback-pull-only-liveness.md`.

### 3.4 `campaign sync` remains user pull

`campaign sync <id> --session-id <s>` attaches, reads the user's acknowledged
cursor and status in one process, prints at most 2,000 tokens, and includes one
liveness line derived from `heartbeat.json`. The factory never invokes it for
progress. Cursor advancement still requires an explicit `campaign ack`; read
and redelivery are safe under rule 2.

### 3.5 Rare actionable session involvement

Only a blocking question, exhausted failover routes or campaign completion may
set `requiresUser: true`. Such an event bypasses ordinary progress handling
and can invoke the session wake bridge. No wake implementation is scheduled
before B4.4, when the preamble ceiling makes rare actionable wakes acceptable.

**Acceptance B1 (release 1).** A replayed run proves bounded event and inbox
records, confirmed-delivery semantics, the 2,000-token `sync` output and
explicit acknowledgement. Healthy progress produces no session wake; human
channels remain available for discrete events; the heartbeat and ambient
status-line proofs are covered by B1.6 and B1.7.

## 5. B3 — Deterministic resilience

What exists at `ca5a93b` and is kept: run-level failover through
`runtimeRules` matching `{ role, status: "exhausted", currentRuntime }` with
`backoffSec`, cycle-checked at validation; bounded structured retry for a
worker result that is not the protocol JSON; live preflight with usage;
detached supervisor adoption of a dead controller; human-channel progress
policy with no control-session wake.

### 5.1 Release 1 scope

| Class | Detection | Response |
|---|---|---|
| Quota with announced reset | driver envelope carries a reset time | reset earlier than the node deadline → the supervisor schedules the retry at reset; otherwise the existing failover edge |
| Quota without reset | envelope | existing failover edge; no edge left → `attention` |
| Transient network | error class and exit code | exponential backoff with jitter, 3 attempts, 2 min cap |
| Protocol (prose instead of JSON) | parse failure | existing bounded repair retry; a second failure records `protocol_failure` and takes the failover edge |
| Dead controller | expired lease | existing |
| Old-version snapshot | snapshot read | advisory, never refuses the run |

`preflight` synthesises default worker failover edges from the healthy
runtimes declared in the contract, ordered by declared `costRank`, unless the
contract declares its own rules. Every synthesized and declared edge is
documented in `references/contract.md` (today undocumented).

Deferred to release 2 (F07/F17): `ENOSPC` GC with an explicit retention
policy that never deletes non-terminal runs; deadline degradation limited to
dropping optional context and downgrading along the route (no runtime node
split, rule 9); `validate --against` once an `expectedFiles` manifest exists.

### 5.2 Derived per-node budget

`budgetForNode = min(maxInvocationTokens, nodeRemaining, phaseRemaining,
1.5 × campaignRemaining / remainingNodes)`, computed by the controller from
the ledger at dispatch. Stops the first node from starving the graph (root
cause 2).

### 5.3 Environment preflight

Before any dispatch: free disk above a threshold, clean worktree, route
runtime binaries present and versioned, `git` functional. A preflight failure
never becomes a lost take.

**Acceptance B3 (release 1).** Replay cases D17, D18, D19, D22, D23 and D31
(network backoff) pass in CI with zero model invocations.

## 6. B4 — Determinism and token economy

### 6.1 Mechanical DoD and conditional judge (protocol schema 2)

Each DoD item declares its proof:

    "definitionOfDone": [
      { "id": "d1", "text": "...", "proof": { "kind": "command", "ref": "npm test" } },
      { "id": "d2", "text": "...", "proof": { "kind": "path", "ref": "results/x.json" } },
      { "id": "d3", "text": "...", "judgment": true }
    ]

`validate` rejects strings and items with neither `proof` nor `judgment:
true`. The shared protocol `schemaVersion` becomes 2 atomically with this
change, in phase 2, under AGENTS.md rule 1: no converter, no dual acceptance;
the persisted-contract budget fallback (`DEFAULT_MAX_INPUT_TOKENS`) goes;
repair contracts generated by `campaign-autonomy.mjs`, judge prompt and
schema in `lib.mjs`, fixtures and examples all move to schema 2. Old run
directories stay readable by the metrics projector through `events.jsonl` and
`usage-ledger.json`, which do not depend on contract validation.

The gate runs mechanical items first; **when no item has `judgment: true`
the judge is not invoked**. When the judge runs it receives the checklist
with deterministic results filled in and arbitrates only judgment items. A
rejection that cites no item id is a judge protocol failure: one bounded
re-ask, then `attention`; it never consumes a revision.

### 6.2 `finalVerification`

New contract-level field with the full verification-command schema
(`argv`, `cwd`, `timeoutSec` up to 600, `repeat`, `env`). The controller
runs it before the judge on the phase-terminal node (a node with no dependant
in the contract), and on any targeted-fix node. Rule 12. The field is
implemented in phase 2 and first consumed by the phase-3 contract: a phase's
controller runs from a snapshot taken before the phase, and `contract.mjs`
rejects unknown top-level fields, so phases 0 and 1 close on the terminal
node's `taskPacket.verification` (`npm test`, 600 s) plus the orchestrator's
own full suite.

### 6.3 `contract prune`

`runner.mjs contract prune <run-dir> --out <file>` writes the continuation
contract with `done` nodes removed and their capsules as seed. A pruned
single-node contract requires `--targeted-fix`, which stamps
`targetedFix: true`; `validate` errors on any other single-node contract.

### 6.4 Documentation diet

Release 1: `SKILL.md` becomes a router plus the load-bearing rules, at most
6,000 bytes, with everything else moved into `references/`; a CI test
enforces the byte ceiling. Release 2: the full split by kind of knowledge
(`rules.md`, `gates.md`, `routing.md`, `recovery.md`), a 24,000-byte
happy-path ceiling, `npm run docs` generated schema blocks with a staleness
check, and a 12,000-byte packet ceiling. Ceilings are bytes; the repository
adds no tokenizer.

### 6.5 Cache-aware ordering (release 2)

Ready nodes ordered by same runtime and same repository prefix.

### 6.6 Worker harness preamble diet (bootstrap, done)

`claude` and `glm` drivers pass `--disable-slash-commands --strict-mcp-config
--setting-sources ""` and `--tools <list>` (runtime field `tools`, default
`Read,Edit,Write,Bash,Glob,Grep`); hooks keep firing so `toolPolicy` stays
true; `--bare` is rejected. The `codex` driver emits
`CODEX_PREAMBLE_OVERRIDES` (browser, computer-use, apps, code-mode host,
multi-agent, MCP servers, plugins off) before the runtime's own `config`, so a
contract can re-enable any of them. Numbers in 0.2. `preflight --json`
(phase 0) makes the measurement mechanical and it is recorded in the journal
at every phase start (rule 13).

**Acceptance B4 (release 1).** A three-node replayed contract without
judgment items closes with zero judge invocations (D24). A rejection citing
no item is invalid (D25). `SKILL.md` under 6,000 bytes with CI green.
`firstPassGateRate` does not regress against phase 0.

### 8.1 Two classes, never mixed

### 8.2 `replay` driver (phase 0)

### 10.3 Ledger and budgets

One ledger epoch for release 1, `2026-09-efficiency-r1v2`, shared by every
phase contract with an identical `usagePolicy` (the ledger enforces one policy
per epoch, so the recalibration required a new explicit epoch; `2026-09-efficiency-r1`
holds only the blocked first take, 125k weighted, and counts as campaign waste
in the retrospective). The epoch cap is a safety net,
not the target: `maxInputTokens` 8,000,000 weighted, `judgeReserveInputTokens`
1,500,000, `maxPhaseInputTokens` 1,000,000 (soft session rotation between
nodes), `maxInvocationTokens` 4,000,000, `cacheReadWeight` 0.1. Each phase
contract sets its own top-level `maxInputTokens` as the phase allowance (phase
0: 2,000,000 weighted) and each node its weighted cap (500k to 700k).

Calibration corrected after the first phase-0 launch (finding N02). Cache
reads are inherent and large: a bounded-preamble worker still re-reads its
whole conversation each turn, so one DeepSeek turn reports about 396,000
cache-inclusive input tokens even though only about 6,000 are uncached. Those
cache reads are cheap only because `cacheReadWeight` is 0.1 (about 40k weighted
per turn), so a multi-turn node lands in the hundreds of thousands weighted
(take17 was 489k for one hard node). Two knobs had to be made consistent with
the weighted campaign meter before any flash worker could run: the per-node
cap (`enforceLedgerBudget` compared raw cache-inclusive tokens) and the
rotation trigger (`ROTATION_AVG_CACHE_READ_TOKENS` compared raw cache reads,
rotating a flash worker on turn one, every turn). `maxInvocationTokens` is the
Codex native rollout budget and counts cache-inclusive tokens, so it is set in
raw terms (4,000,000, about ten DeepSeek turns), not weighted.

The optimisation target stays `weightedPerClosedCheckpoint` below 0.5 M,
measured and reported by `metrics`; the 8 M epoch only stops a runaway.
`timeoutSec` 2400 is the emergency ceiling; the expected node time is 20 to 40
minutes.

## 15. Addendum 01 (2026-09-02)

The owner-approved addendum is versioned at
`ADENDO-01-feedback-pull-only-liveness.md` and is normative for release 1.
It supersedes the progress-wake interpretation of B1.1, all of B1.3, the
affected part of B1.4, the former order-1 session-feedback item and
`sessionOverheadTokens`.

The amended boundary is explicit: the factory pushes only to human channels;
the control session is pull-only and may be involved only for
`requiresUser: true`. B1.6 delivers the atomic, journal-rebuildable 1 KiB
heartbeat, Claude Code ambient status line and macOS notification. B1.7
records harness capabilities only when backed by official documentation.
`campaign sync` remains user initiated and adds heartbeat liveness without
exceeding 2,000 tokens. The rare wake bridge is deferred until after B4.4 and
must never be used for progress.

The addendum introduces ADR-0019 (pull-only session) and ADR-0020
(deterministic ambient liveness), metrics `sessionContextGrowth`,
`sessionWakeCount`, `heartbeatStaleness` and `ambientCoverage`, and evals D27
through D30. Historical release-1 cases D27 and D28 are D31 and D32 in this
master document. Rule 13 is also load-bearing documentation: when the rules
reference is materialized by the documentation-diet phase, it must carry the
same pull-only wording without a second interpretation.
